# Наблюдение за опубликованным сайтом

Навык проверяет уже выложенный сайт практической работы: главную и страницу условия. Источник фактов один — stdout скрипта `scripts/ssg-site-watch.py`. Текст страницы в контекст не берётся.

Метка, которую ищет скрипт, дописывается в каждую страницу хуком `docs-site/hooks.py`: «Хеш коммита», «Дата сборки», «Версия набора данных».

## Назначение

По расписанию или по прямой просьбе узнать, отвечает ли опубликованный сайт и есть ли на проверенных страницах метка сборки. В отчёте каждое поле либо скопировано из JSON скрипта, либо стоит «—».

## Условия срабатывания

Загружать этот навык в двух случаях.

1. Человек спрашивает, открывается ли сайт, отвечает ли GitHub Pages или Helios, на месте ли метка сборки.
2. Сработала запланированная задача с именем `ssg-site-watch`. Её промпт не содержит истории чата, поэтому весь порядок действий берётся отсюда, а список URL — из `targets.json` рядом с навыком.

Рабочее расписание после сдачи замера — раз в 6 часов. Три автономных прогона для отчёта ставятся отдельно, командой cron с `--repeat 3`, и в текст навыка не входят.

## Пошаговая процедура

1. Запустить только эту команду и дождаться завершения:

   ```bash
   python3 ${HERMES_SKILL_DIR}/scripts/ssg-site-watch.py
   ```
2. Разобрать stdout как один JSON-объект. Если процесс не запустился, stdout пустой или это не JSON — остановиться. В ответ записать код возврата и короткий текст ошибки. Страницы самостоятельно не открывать.
3. Не вызывать curl, браузер и web_extract по тем же URL. Повторный запрос в отчёт не идёт.
4. Для каждой записи в targets перенести в отчёт status, http_status, final_url, elapsed_ms, error и три значения из markers. Число null и пустую строку писать как «—».
5. Строку вывода собрать из summary и поля ok. Заново цели не пересчитывать.
6. Если exit_code равен 1 или 2, либо в summary нет ни одного ok и при этом есть source_unavailable или rate_limited, первой строкой ответа поставить ровно [CRON_FAILURE], со следующей строки — отчёт. Так планировщик пометит прогон неуспешным.
7. empty_result, http_error и incomplete — это уже результат наблюдения. Маркер [CRON_FAILURE] для них не ставить, если хотя бы одна цель вернула HTTP-ответ.

## Формат результата

# Сайт ssg-research

Проверка: <checked_at>
Итог: <ok: да или нет>

| Цель | Статус | HTTP | мс | Хеш коммита | Дата сборки | Версия набора данных | Ошибка |
|---|---|---|---|---|---|---|---|
| <name> | <status> | <http_status или —> | <elapsed_ms или —> | <markers… или —> | … | … | <error или —> |

Вывод: <одна строка: какая цель в каком статусе. Для rate_limited указать retry_after или rate_limit.reset из JSON.>
